# Transaction-log mapping capacity

A reader's external buffer has a fixed length. `TransactionLogFile::getMemoryMap()` records the smallest exposed capacity under `fileMutex`; `writeEntriesV1()` refuses a batch whose end would exceed it. The store rotates on no progress, preserving each complete transaction in one segment. The capacity remains recorded after readers release their views.

`writeEntries()` holds `fileMutex` through lazy open, header creation, and the first append, so readers cannot force repeated rotations before an oversized first batch lands. Recovered header-only segments remain readable; an oversized batch rotates away if their capacity was already exposed.

Internal index maps may be replaced before the first reader handout. After exposure, an active map remains pinned so the POSIX writer continues extending its file overlay. Windows releases an undersized internal view before extending the file for a reader's first full-capacity mapping. A requested capacity is always raised to the written extent under the file lock. `Database::Open` rejects `transactionLogMaxSize: 0`: an unbounded segment would outgrow every fixed capacity, so preserving it needs reader remapping or, on Windows, pre-extending the file to the reservation. Internal callers that pass `0` get the default limit from the store constructor.

The JS reader needs no remapping; its filtered-entry transition still refreshes the final extent before leaving a rotated segment, and traversal skips empty retired segments.

# Retention and the sequence witness

Retention deletes any segment that is old enough and lies wholly at or before `txn.state`'s flushed position, including the segment `txn.state` names and the writer's current segment. `doPurge()` retires the current segment from the writer (`retireCurrentSequenceLocked()`) before unlinking it, so a refused unlink leaves an ordinary frozen segment; the next append creates the next segment lazily, as after any rotation.

Once every segment can go, `txn.state` is the only durable record of the highest sequence used. Three rules keep it a sound witness:

- `load()` never appends behind it: with the named segment gone, the writer starts at that sequence + 1, or at the sequence itself when the offset is 0 (a rotation published before the segment was written). Appending lower would land before the position a replay starts from.
- `writeFlushedPosition()` never moves it back, since flush jobs can complete out of order.
- Purge syncs it, and its directory, before unlinking the highest registered segment (`syncFlushedStateForPurge()`), and keeps that segment if the sync fails. Deleting any lower segment leaves a higher file as the record, so only emptying a store pays the fsync, under `writeMutex`. A filesystem that rejects directory fsync keeps that last segment, as before this rule. The record stays an 8-byte in-place overwrite at offset 0, inside one sector, so the flush path takes no extra fsync.

A backup captures `txn.state` before it copies segments, outside the store's locks. `pinRetention()` holds off ordinary purges for that window: a purge reads a newer flushed position and could delete entries the captured one still needs replayed. A stalled backup stream therefore suspends retention for its store until the stream ends.

# Conditional close

`tryClose()` (the only caller is `purgeLogs({ destroy: true })`) may set `isClosing` only when no transaction is bound-but-unwritten (`pendingTransactionCount`) or written-but-uncommitted (a non-sentinel uncommitted position). The two are read in separate critical sections — the count under `transactionBindMutex`, the positions under `writeMutex` + `dataSetsMutex` — and a transaction hands off from one to the other inside `writeBatch()`, so one that binds and writes between the reads is in neither. `transactionBindGeneration` closes that gap: every bind goes through `tryBindTransaction()`, which bumps it, and the latch refuses if it moved since the count was read. A bind that is later abandoned also refuses that attempt; the store stays registered and the next destroy closes it.

Two tighter alternatives are deliberately not used. Holding `transactionBindMutex` while waiting for `writeMutex` would make JS-thread binds wait on retention's file I/O. Try-locking `writeMutex`/`dataSetsMutex` under it would refuse to destroy an idle store whenever a reader, a flush callback, a backup snapshot or a stats call holds `dataSetsMutex`.

# A failed sync freezes the flushed state

`databaseFlushBegin()` syncs every segment before RocksDB flushes, and `txn.state` then records how far the log is covered by flushed data. If any segment sync fails, the store latches `logSyncFailed` and `txn.state` stops advancing for the life of that store instance, reported once through `log.warn`. A later successful sync does not clear it: after a failed `fsync` the kernel may mark the dirty pages clean, so a later success proves nothing about the bytes it lost. The latch is per instance, not persisted: an in-process close and reopen builds a fresh store whose new file descriptors no longer report the earlier error, so the first sync after a reopen can advance `txn.state` again. Holding `txn.state` back has three costs: a longer replay on restart, retention that cannot purge past it, and a lower position for `recoverTail()` to protect (invariant 14), so a crash after the failed sync can discard an unclosed batch's surviving prefix that a later completed flush already put in SST. Advancing it instead could let a restart skip log entries that were never durable.

# Exact-start lookups

`query({ start, exactStart: true })` returns everything from the first entry whose timestamp equals `start`. Timestamps are not ordered (`setTimestamp()` adopts origin and replay timestamps), so a larger timestamp ends nothing. The running-maximum index gives only a lower bound, and a miss used to scan to end-of-log.

A query bounded by `until` takes the stop-to-tail jump only when `mayJumpTo()` proves its target does not pass the other iterator's unread physical position. A span proven timestamp-safe can still cross that boundary. A refusal holds for the rest of the pull, because the bound cannot move until the next pull, which retries.

`TransactionLogStore::findPositionByTimestamp(timestamp, &span)` also returns a span `[stop, tail)` that holds no entry with a timestamp at or below `start`; the reader jumps over it once. Per segment, the index walk keeps two scalars for entries below the running maximum: their minimum timestamp and the end of the last one. The last possible candidate in a segment is then the later of the next maximum key above `start` and, when that minimum is at or below `start`, the last such entry. That gives the same yes/no answer per segment as a full suffix-minimum index. Precision is lost only inside the one segment holding the newest candidate. Memory stays constant per segment, where a suffix-minimum stack grows with every entry below a high outlier.

`tail` is the newest examined byte and moves down to anything the scan must still see. Keep these, each covered by a test:

- **Live tail.** `tail` names the newest _visited_ segment's indexed extent, never `currentSequenceNumber`, which can name a segment not yet created. A match appended later lands past it.
- **Batch boundary.** `tail` is always the start of a batch: the end of a complete walk is the written extent, which `writeEntriesV1` advances only by whole batches, and an incomplete walk or a framing break falls back to the end of the last indexed entry carrying `TRANSACTION_LOG_ENTRY_LAST_FLAG`. A reader that jumps therefore reads the first entry of the next batch, and its flags, before any other entry of it. Logs written before batches were kept within one segment can hold a batch split across a rotation, and a segment with no flagged entry falls back to its header; there the jump lands where a sequential reader crossing the rotation would, at a segment start.
- **Unindexed suffix, framing break, missing sequence.** `tail` stops below each, so the reader still raises `CorruptFrameError` and `TransactionLogGapError` as before.
- **Purge after positioning.** A jump into another segment maps the tail, then re-checks `TransactionLogStore::segmentRemovals` (process-wide, bumped and read under `dataSetsMutex`). If it moved, the reader scans and reports the gap. A start that is already past the stop jumps inside `query()`, so a purge after `query()` returns is ordered after that jump.

The first lookup in a process still indexes every segment from the newest down to the start. The index then persists per segment, so later lookups pay only the walk.

# Iterator handoff

`query({ until })` stops before parsing or filtering any frame at or past the other iterator's unread segment and offset. `done` proves the reader reached that cursor; `endOfReadable` throws if readable input ends short of it. Timestamps cannot express that boundary because commits can arrive with older timestamps.

The bound is not compared per frame. A cursor moves only through its own `next()`, `peek()` or `close()`, and a pull runs none of those on the iterator bounding it (nothing enforces that against a subclass overriding an internal method to advance another iterator; doing so is unsupported), so `next()` turns the bound into one local limit (`scanEnd`): `size`, or the bound's offset when that is nearer in the current segment. It recomputes the limit on entry and after any change to `size` or the segment. The corruption bound (`limit`) is a second per-pull local, recomputed at the same points, and it and `corruptFrame()` read the unclamped `size`: a frame straddling the bound is read whole, and clamping would report it as corrupt and cap the resync search at the bound. `reached` true implies `position >= scanEnd`, so an empty scan falls through to `endOfReadable`, which reports `done`.

A bound must come from the same logical log, which `TransactionLog.equals()` decides natively: `TransactionLogHandle` copies the database's resolved `identityPath` at construction, and `equals()` compares it and the log name. Display paths are not identities: separate databases can use the same relative spelling under different working directories, and an expired store reports no display path. The copy is what keeps the answer stable after either database closes, since the handle's `DBHandle` and store are weak references. Instances carry an N-API type tag, so `equals()` answers `false` for an object another class wrapped instead of unwrapping a pointer of the wrong type. The reader captures `TransactionLog.prototype.equals` at module load, so a subclass overriding `equals()` cannot vouch for a foreign bound. Equality names the logical log, not its generation: a log destroyed and recreated under the same name compares equal (HarperFast/rocksdb-js#1023).

The end of segment S and the header of S+1 are the same frontier, even when rotation has not created S+1 yet. The reader checks that equivalence before probing a successor, and only after covering S's append-owned extent, not merely its committed watermark: a committed reader must still refuse catch-up past a pending uncommitted suffix. Missing intervening sequence numbers cannot be treated as adjacent frontiers.

A cursor used as a bound must be the position the reader will resume from. An unmappable starting segment retains its original sequence and offset; `startUnmapped` retries that mapping before advancing, preserving the positioned offset when it becomes readable. If it is gone, `startMissing` probes successors from below its sequence for the existing gap report, while leaving the advertised cursor fixed until a successor maps.

The private `LogIterator` brand validates bounds without a per-query registry insertion. Its comparison uses the start of a cached `peek()` frame rather than the advanced parsing cursor, including when filtering crossed segments before finding that frame. `peek()` caches only yielded entries, so reaching the current tail does not end future reads. `close()` clears iterator-private references and removes its bound; it does not implement `return()`, preserving resumption after a `for...of` break.

# Aborted batches

`TRANSACTION_LOG_ENTRY_ABORTED_FLAG` (0x02) on a batch's first entry marks a transaction that did not commit. The flag is only on the first entry, so the reader has to find batch starts: an entry starts a transaction after an entry carrying `LAST_FLAG`, at a timestamp change (every entry of a batch carries the batch's timestamp, which recovery also relies on), or when it carries the abort flag itself. An aborted transaction is skipped until the next start, and the state resets at every segment boundary and corrupt-frame resync. So a legacy run that never closed cannot expose an aborted batch, and an aborted batch that lost its last entry hides at most a following batch with the same timestamp in the same segment, which takes corruption plus a reused origin key. A reader that enters an aborted batch past its first entry, or resyncs inside one (the decision is not carried across a resync), reads the rest as live, like the rest of any transaction torn by corruption; on an uncorrupted log no query starts or resyncs there. The validators use the same start rule minus the abort flag itself, and report the flag on an entry that does not otherwise start a transaction. The flag is written only with `transactionLogAbortMarkers` on (see "Abort markers"), so a reader from before it was read is never handed one by default (HarperFast/harper#3253).

# Abort markers

A batch is written before its RocksDB commit, so a transaction that logged and then does not commit leaves a batch that would replay as committed. With `transactionLogAbortMarkers` on, `TransactionHandle::close()` of a handle that logged and did not commit calls `TransactionLogStore::cancelBatch()`: it sets the flag on the batch's first entry (`writeBatch()` reports that address; the watermark key `committedPosition` is not it), syncs, and only then releases the watermark position. Every path that ends a transaction reaches `close()`: `abort()`, orphan collection, a worker's env-cleanup hook (`CloseTransactionsByEnv`, which runs before `ReleaseParkTimeoutsByEnv`), and `finishClose()`'s sweep. Whether a batch is marked is decided by the flag as it was when the attempt that logged it began (`cancelOnAbort`), so turning the flag on or off never changes how an earlier batch ends. The mark and its sync run on whichever thread closes the handle: the JS thread in `abort()` or a GC finalizer for an orphan, a teardown thread otherwise. Only a handle that logged and did not commit pays it.

- **One bit.** The marker is written as `current | 0x02` from the byte as it stands, through a separate non-appending descriptor (Linux `pwrite` ignores the offset on the `O_APPEND` one) or, on Windows, a second handle with explicit offsets, which shares the cache manager's pages with readers' views as appends already do. Nothing else is written. Every mix of old and new bits reads as the old state or the new state, and `0x03` cannot come from a torn `0x01 → 0x03` write without bit `0x01` changing, which neither value does. The residual risk is a sector made unreadable by power loss during the rewrite, the exposure an append that starts mid-sector already has for the committed entries sharing it.
- **Durable before acknowledged.** The marker advances the file's `mutationGeneration`; `syncThrough()` syncs unless a sync since then already covered it. Syncs serialize on `syncMutex`, so aborts waiting at the same moment share one sync. A retry rewrites the byte even when it already reads as set: after a failed `fsync` the kernel may have marked the page clean without writing it, so only a fresh write and a fresh sync make it durable. `flush()` compares the generation as well as the size, so `databaseFlushBegin()` covers a marker that did not grow the file, including on a segment whose descriptor is closed.
- **Fail closed.** A failed marker sync also latches the store's `logSyncFailed` (see "A failed sync freezes the flushed state"): the kernel reports a writeback error once, so this sync may have taken the report for appended pages too. A marker or sync that fails leaves the batch a failed cancellation: its position stays pinned, so committed readers and the flushed state stay behind it and retention cannot purge its segment, and `writeBatch()` refuses new batches while one is unresolved. It is retried before every append, every `databaseFlushBegin()` and store close. An ordinary pending batch, including one parked on a write intent, never blocks appends. `cancelBatch()` is `noexcept`; a failed cancellation that cannot even be recorded refuses appends for the life of the store.
- **Backups.** Once a store has logged a batch with markers on, `snapshotForBackup()` captures the segment sizes and the unresolved positions of batches logged with markers on (`cancellablePositions`; a batch logged with them off resolves as before and is not waited for) under `writeMutex` and `dataSetsMutex` (so no batch is mid-append, its bytes counted while its position still equals the `nextLogPosition` sentinel) and waits for each to commit or be marked, bounded by `ROCKSDB_JS_BACKUP_UNRESOLVED_WAIT_MS`. A copy taken earlier could hold a batch later marked in the live log only, and a restore would replay it. The wait gives up as soon as the database or the backup's handle starts closing: those batches are resolved by the transaction closes that come after the backup's operation drains, so waiting would only stall the close for the full bound.
- **Not undone.** A same-process committed reader never sees an unresolved or aborted batch. A `readUncommitted` reader, or a follower in another process, can read a batch before it is resolved. A crash between the log write and the commit or abort leaves the batch unmarked, and replay redoes it.

# Reader mappings are SharedArrayBuffers

`createMemoryMapBuffer()` (`transaction_log.cpp`) hands a mapping to JS as a `Buffer` over an external `SharedArrayBuffer` when the runtime exports `node_api_create_external_sharedarraybuffer` (Node 24.16+; on Windows from the executable, `libnode.dll` or `node.dll`), and falls back to `napi_create_external_buffer` elsewhere. `supportsSharedTransactionLogMaps()` reports whether the shared path is available (the API is exported and the addon could be pinned); an individual mapping still falls back to an external `Buffer` if creating its shared buffer fails. V8 counts an external `ArrayBuffer`'s bytes toward its external-memory limit (`BackingStore::PerIsolateAccountingLength()` returns 0 only for shared and empty-deleter stores). From V8 15 (Node 27), once retained external bytes pass about twice the heap limit, every further external allocation forces a full mark-compact that cannot free them: holding 32 GB of 16 MiB maps cost 3,324 full GCs (370 s) with a 1.5 GB live heap, against none for the shared path. A mapping costs address space, not heap, so it is kept out of that budget.

Consequences of the shared backing store:

- The finalizer runs when the last backing-store reference drops, on whichever thread drops it, not on the JS thread. It may only delete the `MemoryMap` handle, whose destructor unmaps and decrements an atomic.
- The finalizer can run after the addon is unloaded. Node closes a worker's addons in its environment teardown, before the isolate's remaining backing stores are released, and a store shared to another thread can outlive the worker entirely. `pinAddon()` therefore pins the module (`GET_MODULE_HANDLE_EX_FLAG_PIN`, `RTLD_NODELETE`) before the shared path is first used, and the fallback is taken if pinning fails.
- Nothing pressures GC to release a dropped mapping; it is unmapped when ordinary JS allocation triggers a collection. A worker that drops mappings and then goes idle keeps them mapped.
- `buffer.buffer` is a `SharedArrayBuffer`: `instanceof ArrayBuffer` is false, `new Blob([buffer])` throws from Node 27, and `structuredClone`/`postMessage` share the mapping instead of copying it.

The function is looked up at runtime (`dlsym`/`GetProcAddress`), not linked, so one binary still loads on Node 22, Bun and Deno: a link-time import of a missing export fails the Windows DLL load, and elsewhere aborts on first call.

# Purge watermark

`<store>/txn.purged` holds the store's purge watermark `W`, at or above every entry key of every segment the store deleted, plus a `known` flag and a sequence `T`. `log.getPurgeWatermark()` reports `W` only while `known`.

- **Durable before unlink.** `doPurge()` first chooses every segment it will delete and resolves each one's largest key, then persists `max(W, those keys)` and `T = max(T, lowest retained sequence after the purge − 1)`, and only then unlinks. A failed write deletes and forgets nothing. A failed unlink, or a crash after the write, leaves survivors at or below `T` that `W` already covers, so the record never needs correcting afterwards.
- **Largest key, proven.** A segment this process created tracks it on append (`appendMaxExact`). Any other segment is read with `scanMaxEntryTimestamp()`, the timestamp-floor scanner, which proves it saw every durable key. The query index (`positionByTimestampIndex`) cannot prove that: it is lazy, covers a prefix, includes the header's timestamp slot, and can stop at a zero word that hides a later frame. A segment the scanner reports as corrupt is still purged and makes the store unknown, so corruption cannot stall retention. An I/O error, or the per-run scan budget running out, keeps the segment for a later run. `scanPurgeCandidates()` reads them before the purge takes `writeMutex`, the idle current segment included; a current segment's result is kept only while its `size` is unchanged, since appends only grow it.
- **Two slots, a sector apart.** Each write goes to the slot that does not hold the current record, then syncs, so a torn write leaves the previous record valid. A purge needs no directory operation. Both slots unreadable reads as unknown.
- **Baseline rule (`loadPurgeRecord()`).** The watermark is known only when a valid record says known and every sequence in `(T, writer's next sequence)` is still on disk. When the writer's next sequence is `T` itself (a purge chose the current segment and stopped before its unlink), load retires that segment first, as it does for a segment `txn.state` names, so no key lands in a sequence the record covers. That check catches an older release's retention (it deletes segments without updating the record) and a reused sequence space. A partial directory listing (`discoveryIncomplete`) or an unreadable record proves nothing either way, so that open reports unknown without persisting it. Every write takes a generation above the newest on disk and keeps the disk's watermark when it is higher (`writePurgeRecord()`), so a store whose in-memory record is behind cannot overwrite the newer slot. The exception is a retry of the store's own write whose sync failed: that write may never reach the disk, so the retry rewrites its slot and leaves the last durable one alone. A store without a record is unknown even when its directory is empty: only `ResolveStore` creating the directory (`initializeNewPurgeRecord()`) proves a store is new, and only a caller's baseline can make it known (see "Purge baseline"). The check cannot detect files removed outside rocksdb-js, nor an older release reusing sequences at or below `T` after `txn.state` was removed. The documented downgrade procedure therefore removes `txn.purged` as well.
- **Destroy** durably marks the record unknown (`invalidatePurgeRecord()`, which writes one where none exists) before its purge, its close and the directory removal, which deletes everything but the record in no fixed order, can stop part-way, and removes unflushed segments the record never covered. If that write fails, the store stays open and registered with every file. A store recreated under the same name after the directory is gone starts a new history at 0; one that outlived the destroy, or was recreated before it finished, keeps the unknown record.
- **Backups** capture the record under the same lock as the segment list. A segment that vanishes before it is copied (only a destroy or an out-of-band delete can, since the retention pin holds purges off) makes the backed-up record unknown (`backupInlineContents()`).
- **Read-only opens** re-read the record on each call and combine it with their own load-time check, since a writer in another process may purge after they open. A generation lower than one already read, or a damaged other slot, can mean a newer record was lost after its purge ran, so either reads as unknown.
- Close and rotation never delete segments (`doClose()` empties `sequenceFiles` before its `doPurge()` call), so `doPurge()` is the only path the record has to cover.

# Purge baseline

A store created before the record has deletions nothing recorded, so only a caller can bound them. The record's `tracked` flag says every deletion since the record began is folded into `W`; `known` implies it. `setPurgeBaseline(B)` makes a tracked, unknown record known at `max(W, B)`.

- **Where a record begins.** The first writable open of a store with no record (`loadPurgeRecord()`, complete listing) writes it tracked with `T` one below the lowest registered sequence, or the writer's, so everything at or below `T` predates it. The continuity check then runs as for a known record: an interior hole refuses tracking at once. A read-only open writes nothing and vouches only for a record it opened with.
- **Losing it.** Every path that loses coverage calls `TransactionLogPurgeRecord::loseCoverage()`, clearing both flags, and a merge with a newer disk record ANDs both. Nothing sets `tracked` again except a new record.
- **Adoption** holds `writeMutex` and `dataSetsMutex`, so no purge lands between the read and the write, refuses a store already closing, and writes the flag and the value into one slot: a torn write leaves the previous, unknown slot. The value holds from the moment the slot is written, so a follower reading an unsynced adoption sees a correct bound, and a later write that reuses the failed slot only returns the record to unknown.
- **Encoding.** `0x02` is written only without `0x01`, so 2.14.0 still reads known records and rejects a tracked-only slot (unknown); its own rewrite carries no `tracked` bit. After adoption the older slot still holds the tracked-only record, which 2.14.0 treats as a damaged slot: its writable open rewrites it, and its read-only or secondary open reports unknown until the next record write here replaces that slot. An unknown record 2.14.0 wrote is never adoptable: it cannot say why it is unknown.
- **No silent restart.** An absent record reads as a store that predates the record, so a record must not vanish while its store lives: `createRecordFile()` removes a new record whose directory sync failed, `removeTransactionLogStoreDirectory()` deletes it last (and puts back an unknown one if the directory still outlives it; behind a symlink or junction it removes only the store's own regular files, then the link), and a destroy's own purge keeps it (`keepRecord`), since a bound transaction can keep the store alive past the destroy. The registry erases a destroyed store and removes its directory under `storesMutex`, so a `useLog()` cannot build a store over a directory that is then deleted under it. A `useLog()` from another thread that replaces the closing store before the destroy erases it inherits that record too: telling a destroyed closing store from one closing with its database, and clearing its directory on the open path while its files may still be closing, would cost more than a log that stays unknown. Such a store stays unknown until a later destroy removes it. Removing it by hand (the documented downgrade step) or losing its name on a filesystem without directory sync starts a new record, and a baseline for it has to cover everything deleted before it, including what an earlier watermark covered.
